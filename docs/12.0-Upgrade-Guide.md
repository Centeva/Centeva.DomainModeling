# Upgrading to 12.0

Version 12 tightens the library's DDD guardrails while decoupling its
abstractions from specific implementations.  Repository interfaces now enforce
aggregate-root semantics at the type level, `BaseEntity<TId>` constrains its
key type, domain event dispatch is expressed through a small interface instead
of a base class, and a couple of `int`-biased conveniences have been removed.
The result is a baseline that steers consumers toward correct DDD usage while
leaving them free to choose their own implementations.  The changes below are
breaking but the migration is mechanical.

To summarize, the main changes are:

* `IRepository<T>` and `IReadRepository<T>` now require `T` to implement
  `IAggregateRoot`, enforcing at the type level that repositories only operate
  on aggregate roots.
* The non-generic `BaseEntity` convenience class (which defaulted the `Id` type
  to `int`) has been removed.  Inherit from `BaseEntity<TId>` and specify the
  key type explicitly.
* `BaseEntity<TId>` now constrains `TId` to `struct, IEquatable<TId>`.  Both
  `int` and `Guid` satisfy the constraint, so most existing entities need no
  changes.
* `ObjectWithEvents.ClearDomainEvents` is now `public` and `DomainEvents`
  returns `IReadOnlyCollection<IDomainEvent>` instead of `IEnumerable<IDomainEvent>`.
* Domain event dispatchers now work against a new `IHasDomainEvents` interface
  instead of the `ObjectWithEvents` base class.

## Mark aggregate roots with `IAggregateRoot`

**Why this changed:** In Domain-Driven Design, an *aggregate* is a cluster of
related objects treated as a single unit for the purpose of data changes.  The
*aggregate root* is the one entity in that cluster that outside code is allowed
to reference and load — it acts as the consistency boundary that protects the
aggregate's invariants.  A common DDD rule is that **repositories only exist
for aggregate roots** — child entities inside the aggregate are loaded and
modified through the root, not fetched independently.

Previously `IAggregateRoot` was a marker interface that the library defined but
did not enforce, so it was easy to accidentally create a repository for a child
entity.  Adding the constraint makes the compiler enforce the rule for you.

`IRepository<T>` and `IReadRepository<T>` now include a `where T : IAggregateRoot`
constraint.  For every entity type that you use with a repository, apply the
`IAggregateRoot` marker interface:

```csharp
// Before
public class Customer : BaseEntity<Guid>
{
    // ...
}

// After
public class Customer : BaseEntity<Guid>, IAggregateRoot
{
    // ...
}
```

Any repository base class or in-memory fake you have written needs the same
constraint propagated:

```csharp
// Before
public class MyRepository<T> : BaseRepository<T> where T : class { }

// After
public class MyRepository<T> : BaseRepository<T> where T : class, IAggregateRoot { }
```

Child entities inside an aggregate (for example, an `OrderLine` inside an
`Order`) should *not* be marked as aggregate roots and should not have their
own repositories.  Access them through their aggregate root.

## Specify the key type on `BaseEntity<TId>`

**Why this changed:** The non-generic `BaseEntity` class was a shortcut for
`BaseEntity<int>`.  In practice, this quietly recommended `int` as the default
key type — but auto-incrementing integer keys are usually a poor fit for DDD.
They can only be assigned by the database (so an entity is not fully-formed
until it has been saved), they leak information about the order and volume of
created records, and they are awkward in distributed or offline-first systems.

DDD baselines more commonly use `Guid` (or a strongly-typed ID wrapping a
`Guid`), which can be generated in-process before persistence and carries no
implicit ordering.  Removing the non-generic shortcut forces you to make an
explicit choice rather than falling into a default that may not fit your
domain.

The non-generic `BaseEntity` class has been removed.  For any entity that
inherited from it, specify the key type explicitly:

```csharp
// Before
public class Customer : BaseEntity, IAggregateRoot
{
    // ...
}

// After
public class Customer : BaseEntity<Guid>, IAggregateRoot
{
    // ...
}
```

Use whatever key type is appropriate for your domain.  `Guid` is a common
default; `int` remains available if a database-assigned integer key is what
you want.

The `FakeRepository<TEntity>` convenience class (which used
`FakeRepository<TEntity, int>`) has also been removed for the same reason.
Use `FakeRepository<TEntity, TKey>` and specify the key type explicitly:

```csharp
// Before
var repository = new FakeRepository<Customer>();

// After
var repository = new FakeRepository<Customer, Guid>();
```

## Constrain your ID type to `struct, IEquatable<TId>`

**Why this changed:** `BaseEntity<TId>` now expresses two guarantees the
library previously relied on informally: IDs are never null, and they support
boxing-free equality.  The `struct` part rules out `record class` ID wrappers
and `string` keys (both of which are reference types and can be null); the
`IEquatable<TId>` part guarantees that identity comparisons don't box the
value.

Both `int` and `Guid` &mdash; the two common choices &mdash; satisfy the new
constraint, so most entities need no changes.  If you were using a strongly-
typed ID as a `record` or `record class`, switch it to `readonly record struct`:

```csharp
// Before
public record CustomerId(Guid Value);

// After
public readonly record struct CustomerId(Guid Value);
```

`readonly record struct` is a better fit for IDs anyway: they are small,
immutable values, and using a struct avoids per-ID heap allocations while
still giving you value equality and a concise declaration syntax.

If you were using `string` as an ID type, you'll need to switch to a struct-
based key.  Wrapping the string in a `readonly record struct` is one option;
switching to `Guid` is another.

## `ObjectWithEvents` API surface changes

**Why this changed:** `ObjectWithEvents` now implements the new
`IHasDomainEvents` interface (see the next section) so that consumers of the
event machinery can depend on an interface rather than a concrete base class.
Interface members must be `public`, so `ClearDomainEvents` — which was
previously `internal` — has been widened.  As a bonus, this removes a subtle
issue where custom `IDomainEventDispatcher` implementations outside the core
assembly could not clear events without `InternalsVisibleTo` gymnastics.

The `DomainEvents` return type was also tightened from `IEnumerable<T>` to
`IReadOnlyCollection<T>`.  This more honestly describes the value (a
materialized snapshot, not a lazy query) and lets callers use `.Count` without
enumerating the sequence.

If you were relying on `InternalsVisibleTo` or reflection to call
`ClearDomainEvents`, note that it is now `public` and can be called directly.

`DomainEvents` now returns `IReadOnlyCollection<IDomainEvent>` instead of
`IEnumerable<IDomainEvent>`.  This is source-compatible for most callers (all
`IEnumerable<T>` operations still work), but code compiled against the previous
signature will need to be recompiled.

## Prefer `IHasDomainEvents` over `ObjectWithEvents` in signatures

**Why this changed:** Previously, any code that wanted to work with
"an entity that can raise domain events" had to reference the `ObjectWithEvents`
concrete base class.  That forced every entity to inherit from a specific type
chosen by the library, and ruled out records, structs, or entities that
already inherit from another base class.

The new `IHasDomainEvents` interface expresses the *capability* without
dictating the *implementation*.  `ObjectWithEvents` remains a convenient base
class that provides an event list and a protected `RegisterDomainEvent` method,
but it is no longer the only way to participate in domain event dispatching.

Any code that referenced `ObjectWithEvents` as a parameter, return type, or
generic argument should be updated to use the new `IHasDomainEvents` interface.
`ObjectWithEvents` remains the recommended base class to *inherit* from (via
`BaseEntity<TId>`), but the interface is the correct type to depend on
elsewhere.

For example, if you have any custom EF Core interceptors, LINQ queries over the
change tracker, or utility methods that operate on entities-with-events:

```csharp
// Before
context.ChangeTracker.Entries<ObjectWithEvents>()

// After
context.ChangeTracker.Entries<IHasDomainEvents>()
```

## Update custom `IDomainEventDispatcher` implementations

**Why this changed:** This is a direct consequence of the previous section.
The dispatcher's contract used to be phrased in terms of `ObjectWithEvents`,
which meant every dispatcher was coupled to that specific base class.
Switching to `IHasDomainEvents` frees consumers to raise events from any type
that implements the interface, without changing the dispatcher.

`IDomainEventDispatcher.DispatchAndClearEvents` now takes
`IEnumerable<IHasDomainEvents>` instead of `IEnumerable<ObjectWithEvents>`.

If you only use the provided `MediatRDomainEventDispatcher` or
`MediatorDomainEventDispatcher`, no change is required.

If you have a custom implementation, update the parameter type:

```csharp
// Before
public Task DispatchAndClearEvents(
    IEnumerable<ObjectWithEvents> entitiesWithEvents,
    CancellationToken cancellationToken = default)
{
    // ...
}

// After
public Task DispatchAndClearEvents(
    IEnumerable<IHasDomainEvents> entitiesWithEvents,
    CancellationToken cancellationToken = default)
{
    // ...
}
```

The body of the method typically only calls `.DomainEvents` and
`.ClearDomainEvents()`, both of which are on the new interface, so no further
changes are usually needed.
